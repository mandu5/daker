# 팀 구성 및 실행 제약

## 참가 형태

**1인 개인 참가** (mandu5). 팀원 추가 없음.

대회 규정상 개인 참가가 허용되며(최대 3명까지 가능하나 우리는 1인),
심사에서 팀 규모에 따른 가점·감점 항목은 없다.

## 이 제약이 제안서에 미치는 영향

### 1. 실행 계획의 신뢰성 (루브릭: 기술적 실현 가능성 20점)

본선 개발 기간은 4주(2026-09-07 ~ 10-02)다. 1인이 4주에 만들 수 있는 범위를
정직하게 잡아야 한다. 심사위원 중 엔지니어링 관점 평가자는 "말은 그럴싸한데
실제로 못 만드는 제안서"를 가려내려 한다. 3인 팀 기준의 과대한 범위를 적으면
오히려 감점 요인이 된다.

→ **대응**: 범위를 좁고 깊게 잡는다. 핵심 루프 하나를 끝까지 작동시키고,
확장 가능성은 구조로 보여준다. 예선 단계에서 이미 동작하는 프로토타입을
제시해 "1인이 이만큼 이미 만들었다"는 실물 증거로 실현 가능성을 입증한다.

### 2. AI 활용 투명성 서사 (루브릭: 연구 윤리 및 완성도 10점 / 항목 5)

템플릿 항목 5는 "제안서 작성 및 에이전트 설계 과정에서 AI를 연구동료로서
어떻게 활용했는지 명시"를 요구한다.

1인 참가자가 에이전틱 AI를 써서 에이전틱 AI를 설계·구현했다는 사실 자체가
이 항목의 가장 자연스러운 답이다. 실제 사용 기록(모델명, 프롬프트 설계,
검증 절차, AI 산출물 중 무엇을 채택하고 무엇을 기각했는지)을 남겨두면
형식적으로 쓴 다른 팀 대비 확실한 차별점이 된다.

→ **대응**: 작업 과정의 AI 활용 로그를 `docs/` 에 실제로 축적한다.
제안서에는 요약본과 검증 절차를 싣는다.

### 3. 리소스 추정 (항목 7: API 및 GPU 예상 소요 규모)

1인 기준의 현실적인 토큰·호출량·GPU 시간을 산정한다. 과다 청구는
"리소스 활용 효율성"(본선 15점) 관점에서 불리하다.

### 4. 자동화가 곧 경쟁력

1인이라는 제약은 곧 "사람 손이 적게 드는 구조"를 설계할 강한 동기가 된다.
평가 하네스, 회귀 테스트, 문서 빌드를 전부 자동화해 두면 4주 개발 기간에
사람은 판단에만 집중할 수 있다. 이 자동화 자체를 제안서의 실현 가능성
근거로 제시한다.

## 현재까지 구축한 자동화 (실현 가능성 증거)

| 자산 | 위치 | 역할 |
|---|---|---|
| hwpx 생성기 | `tools/hwpx/hwpxbuild.py` | 원고(블록 DSL) → 제출 규격 hwpx 자동 생성 |
| 문서 미리보기 | `tools/hwpx/preview.py` | 동일 용지 기하 PDF 렌더 → 10쪽 제한·시각 완성도 검증 |
| 도식 렌더러 | `tools/figures/figure.py` | 아키텍처도 300dpi PNG 자동 생성 |
